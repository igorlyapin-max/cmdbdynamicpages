# Проверка Гипотез Качества Assistant: 2026-09-05

## Объем Работы

В `testtemplate3` восстановлен текст сопоставления размещений и связей из версии 6
в текущее поле `authoring.assistant.diagramIntentPrompt`: 3470 символов. Изменилось
только это поле и служебные дата/хеш сохранения. Выборки, D2 source, сохраненный
анализ и настройки диаграмм не заменялись исторической версией.

На момент начала восстановления `result.diagrams` уже был пустым. Возврат промта
не восстанавливает отсутствующий примененный mapping и не генерирует диаграмму.
Историческая версия используется только для разового восстановления текста;
поддержка legacy runtime не добавлялась.
Причина прежнего исчезновения текста по имеющимся снимкам достоверно не
установлена. Проверен текущий путь сохранения; восстановление не следует считать
исправлением доказанного дефекта этого пути.

В обычном UI проверены видимость текста, Save, переключение меню и шаблона,
reload и новый browser context. Дополнительно выполнена загрузка без перехвата
запросов: автоматическое восстановление анализа вернуло 200, prompt остался
видимым, сохраненная карточка не изменилась. Расширенный изолированный browser
regression прошел; созданные тестовые шаблоны удалены.

Модель: настроенный alias `corp-openai-gpt-4.1-mini`, temperature 0.1,
output bound 2400, concurrency 2, максимум один repair на стадию. Alias совпадал

Во время настройки harness отдельно исправлена классификация: транспортный сбой

## Повтор Реального Binding-Этапа

Снимок содержит 13 бизнес-блоков, 18 незавершенных размещений и 3 типа связей.
Использованы production message builder, seed, normalization и validator;
JSON-ответы не применялись к шаблону. Проверяется первый проход binding-intent,
без автоматического repair, последующей генерации DSL или исполнения диаграммы.

| Проверка, 3 повтора | Принято | Вызовов | Среднее время этапа |
| --- | ---: | ---: | ---: |
| Текущие инструкции, 2400 output tokens | 0/3 | 3 | 12.6 с |
| Те же инструкции, 8192 tokens | 0/3 | 3 | 10.8 с |
| Пакеты по 6 целей, 2400 tokens | 0/3 | 12 | 38.2 с |
| Убрано одно противоречие в инструкции, 8192 tokens | 0/3 | 3 | 10.7 с |

Во всех 12 результатах сохранена одна ошибка: `endpointMode=dataFields` для трех
типов ACL. `dataFields` описывает направление, а допустимые способы сопоставления
концов включают `attributeEndpoints`, `relationCard`, `deterministicEndpoints`.
Количество токенов не было непосредственным препятствием: ответы завершились
нормально. Во всех результатах поля сопоставления объектов `endpointFields` пустые.

После основного сравнения выполнены еще 3 диагностических вызова с явным
различением `endpointMode` и `directionPolicy`, допустимыми значениями и
контрпримером. Ошибка `dataFields` исчезла; binding validator принял 2/3 ответов.
Это **не улучшение полноты диаграммы**: во всех трех ответах endpointFields
объектов остались пустыми, а назначение ACL описано полем `range` вместо
адреса назначения `dipaddress`. Один ответ также содержал неподдерживаемую форму
membership `RelatedId = parent._id`. Этот post-hoc опыт показывает пользу точного
словаря, но одновременно недостаточность одной проверки принятия контракта.

Первый калибровочный replay был остановлен после обнаружения отличия его фильтрации
ответов от production. Он не включен в таблицу. Исправленный вариант ограничивает
ответы целями каждого запроса и проверяет полноту после объединения; это закреплено
тестом. Расход этих предварительных диагностических вызовов не включен в стоимость
синтетического пилота.

## Подтвержденные Пробелы Контекста

1. Системная инструкция binding запрещает поля/operators/connection mode, а ниже
   требует извлечь их из Notes. Удаление только этой фразы недостаточно: результат
   отдельного контролируемого сравнения выше не улучшился.
2. Ручной mapping `testtemplate2` использует для ИС путь
   `{ISZabbixMonitoringDomain:ipRange}.range`. В terminalFields блока «Внешние ИС»
   binding получает только `Class`, `_id`, `Code`, `Description`, `Name`, `isExt`.
   Terminal contract упоминает сравнение с `range`, но не предоставляет этот путь
   как доступное поле результата. Требование использовать только подтвержденные
   поля нельзя исправить просьбой угадать недостающее поле.
3. Ручной mapping различает карточку сервера и приложения в одной строке пары.
   Бизнес-название результата без выбранной стороны пары не фиксирует identity,
   label и endpoint attribute отображаемого узла.
4. Возврат 18 business bindings не равен полноте диаграммы: нужны также атрибуты
   концов, branch filters, membership и явная сторона пары. Действующий план
   экспериментов должен оценивать эти обязательства отдельно от валидного JSON.
5. Текущие Notes называют `scope_vlan` и `scope_server` «статическим контейнером»,
   а восстановленный prompt требует повторять их по карточкам. Notes имеют
   приоритет; модель выбирала structural без источника. Это конфликт описаний,
   а не доказательство отсутствия серверов. Нужно отдельно задавать **число
   экземпляров**, **источник данных** и **участие в стрелках**. «Не участвует в
   стрелках» не означает «вывести один раз».

## Следующий Проверяемый План

1. Зафиксировать независимый oracle по объектам, сторонам пар, экземплярам ветвей
   и стрелкам. Ручной `testtemplate2` считать кандидатом в эталон, проверить ACL
   отдельно: 20 строк при 16 карточках нельзя механически превращать в 20 стрелок.
2. В предметном описании результата задавать: основной объект, дополнительные
   связанные данные, условия включения, ожидаемую гранулярность. Технические
   stage IDs и JSON-поля пользователь не обязан писать.
3. Подать Assistant подтвержденный каталог доступных полей выбранных результатов,
   включая пути связей на настроенную глубину и сторону пары. Ограничивать его
   релевантными полями задачи, не полным каталогом CMDB. В Help описывать смысл
   reference/domain, направление, cardinality, формат значения, null/пустой набор,
   различие основного и management адреса. Не хранить в Help ответы конкретного отчета.
4. Разделить словари binding: тип элемента, повторение, membership, endpoint method
   и направление. Для каждого дать допустимые значения, положительный пример и
   контрпример. Notes содержат бизнес-ограничения; машинные directives остаются
   необязательным точным способом зафиксировать решение.
   Вместо двусмысленного «статический scope» писать, например: «Для каждой карточки
   выбранного результата создай отдельную рамку; внутри один узел этой карточки;
   рамка не является концом стрелки». Для настоящей статической группы: «Одна
   рамка в этой ветви, число ее экземпляров не зависит от количества карточек».
5. Выбирать из подтвержденных альтернатив, затем компилировать исполнение кодом.
   Детерминированно известные правила не генерировать повторно. Пропуск обязательного
   endpoint field или выбор не той стороны пары должен оставаться видимым пробелом,
   а не зеленым «все сопоставлено».
6. Сравнить согласованный контекст и типизированные инструкции отдельно, затем вместе.
   Для каждого подхода повторить полный путь на копии шаблона: семантика данных,
   Object Flow, извлечение, семантика D2, размещения, иерархия, связи, preview.
   Никаких Save/Apply поверх пользовательского шаблона для эксперимента.
7. Допуск к изменению общего поведения: все обязательные объекты и связи эталона
   присутствуют, лишних нет, все условия и identity сохранены. На holdout отдельно
   измерить exact row sets/multisets, hierarchy/edge sets, false acceptance, unresolved,
   число ручных исправлений, p50/p95, токены и стоимость. Новая модель/alias или
   изменение данных требует нового freeze; подгонка по holdout запрещена.

Полный pipeline по новым гипотезам пока не проверен и улучшенным не объявляется.
В этой работе изменены текст восстановленного промта, исследовательские инструменты
и regression-тест; общие runtime-промты, Object Flow и renderer не изменялись.
